# 单位与坐标契约

这份契约必须在**第一件几何被创建之前**写进项目文件，并且在任何 `overlay` / `IoU` / `probe` / 建模动作之前通过往返预检。它的存在是因为真实事故：两套口径混用，让一整轮「原画对照」整体缩放约 0.6 倍，结论全部作废。

---

## 一、为什么值得单独写一份契约

项目里通常同时存在两套能把「像素」和「毫米」联系起来的口径：

| 口径 | 用途 | 典型来源 |
|---|---|---|
| **几何口径** | 把原画像素换算成世界坐标（建模用） | 由参考图实测反推，如 `K = 目标高度 / 图上像素高度` |
| **相机正交口径** | 把世界坐标投回渲染图（对照用） | 由 `ortho_scale` 与渲染分辨率决定 |

两者数值接近但**语义不同**，混用不会报错，只会让所有对照结论整体偏一个比例。所以：

> `UNIT_CONVENTION.md` 必须逐项写明「哪套口径用在哪里」，并声明唯一 source of truth。

---

## 二、选定场景单位：`1 Blender unit = 1 mm`

3D 打印件的自然口径。在**第一件几何创建之前**执行一次：

```python
import bpy
scene = bpy.context.scene
scene.unit_settings.system = 'METRIC'
scene.unit_settings.scale_length = 0.001   # 1 unit = 1 mm
scene.unit_settings.length_unit = 'MILLIMETERS'
```

由此产生的硬性口径：

- 所有落盘数值（尺寸、深度、偏移）都是**毫米**，脚本里不再做单位换算；
- 相机裁剪距离、灯光距离、体素尺寸等派生量同步放大 1000 倍；
- 导出时确认导出器没有二次缩放（见「五、导出前的三项实测」）。

> 例外：如果项目主体是建筑/场景（米级），就用 `scale_length = 1.0`，但要在契约里写明，并同步换算全部打印相关阈值。

---

## 三、像素 → 毫米：常数怎么定、怎么验

**定**：不要用「图片宽度 / 目标宽度」这种二手换算。用**参考图上两个已知语义点的距离**反推：

```
K = 目标实际长度(mm) / 图上该长度的像素数
```

示例（真实项目）：目标总高 120 mm，参考图对应高度 296 px → `K = 120/296 = 0.405405`；另一项目标定 `K = 200/296 = 0.675676`。**数值随项目变化，不要跨项目复用。**

**验**：取图上 3 个以上**独立**已知点（不要都用同一条边上的点），把它们换算成世界坐标，与预期值比对；误差超出容差就重标定。

**记**：`K`、原点像素、朝向映射（哪个像素方向对应 +X / +Z）、深度符号，全部写进 `UNIT_CONVENTION.md`，并给出可执行的换算函数。

## 四、坐标往返预检（唯一准入闸门）

链路：`SRC(源图像素) → WORLD(世界坐标) → CAMERA_PIXEL(渲染图像素) → SRC`。

- 至少 **5 个已知点**，应覆盖画面四角与中心，而不是集中在中间一条线上；
- 每点往返误差 **≤ 0.5 源像素**；
- 任一点超差 → **立即停止**，不允许继续 overlay / IoU / probe / 建模。

脚本：`../tools/unit_roundtrip_check.py`。它按下面的模型做完整往返：

```
几何口径（src → world）：
    X = (px - ox) * K
    Z = (oz - py) * K        # py 向下增大
相机正交口径（world → pixel）：
    s  = ortho_scale / max(W, H)      # Blender 的 ortho_scale 作用于渲染较长边
    u  = W/2 + (X - cx) / s
    v  = H/2 - (Z - cz) / s
```

把这两段串起来再反转回来，与源像素比较。**它同时是「口径混用」的探针**：如果你把几何口径的 `K` 当成相机的每像素世界尺度（或反之），往返残差会立刻超差——这正是那场 0.6 倍事故的形状。

用法：

```powershell
python tools/unit_roundtrip_check.py --spec roundtrip.spec.json
python tools/unit_roundtrip_check.py --spec roundtrip.spec.json --write-report shots/roundtrip_report.json
```

`spec` 里只写 src 像素即可，脚本自己走完三段；也可以给 `world` 做单段交叉验证。完整字段见脚本头注释与 `--help`。

## 五、导出前的三项实测

导出 STL / FBX 之前，把这三项**打印出来**贴进交付说明：

1. `scene.unit_settings.system / scale_length / length_unit` 的实际值；
2. 全部待导出对象的 `scale` 是否均为 `(1, 1, 1)`（有非单位缩放就先应用）；
3. 导出后**重新导入**一个副本，实测 bbox 与目标尺寸（例：总高 120.0 mm ± 0.1），并给出读回报告。

第二条最容易被跳过：`scale != (1,1,1)` 时，Blender 里看到的尺寸与导出文件里的尺寸可以不同。

---

## 六、区间、bbox 与深度带的闭开约定

- 逐行/逐列比较时，**写明区间是 `[lo, hi]` 还是 `[lo, hi)`**，并在所有脚本里用同一前缀常量表达；
- `bbox` 的边界归属（行/列是否含端点像素）单独写明；
- 深度带（层）给**下限与相邻层余量**，不要只给一个中心值：判定「不跨层」比判定「等于某个数」稳定得多。

这三条合起来解决的是同一类问题：**同一份几何，两个脚本算出不同的行数**。

## 七、变更记录与下游回归

单位或换算常数一旦改动：

1. 在 `UNIT_CONVENTION.md` 追加变更记录（谁、何时、改了什么、为什么）；
2. 列出**必须重跑的下游检查**：深度表、判定阈值、相机参数、导出缩放、此前所有对照报告；
3. 重跑后把旧结论标记为「作废（口径变更）」，不要留在台账里当现行事实。

> 真实案例：`UNIT_CONVENTION.md` 里的 `K` 小数展开写错了一位，虽然脚本用的是精确分数、几何没受影响，但文档与实现不一致本身会被下游当作权威引用。**文档里的数值必须由脚本输出回写，不手抄第二套。**

## 八、交付时的单位报告格式

```markdown
## 单位报告

| 项 | 值 | 来源 |
|---|---|---|
| 场景单位 | METRIC / scale_length = 0.001（1 unit = 1 mm） | scene.unit_settings 实测 |
| 几何口径 | K = 120/296 = 0.405405 mm/px；原点 src(141.5, 402.0) | UNIT_CONVENTION.md §3 |
| 相机口径 | ortho_scale = 145.0 mm，渲染 296×402 → 0.489864 mm/px | 渲染脚本输出 |
| 往返预检 | 5/5 点通过，最大残差 0.31 src px（容差 0.5） | shots/roundtrip_report.json |
| 导出尺寸 | 总高 120.00 mm，总宽 90.22 mm，厚 6.50 mm（STL 读回实测） | check_stl_reimport.json |
| 对象缩放 | 全部 (1, 1, 1) | 导出前实测 |

未解决：底座中心与脚底接触区中心的水平偏移约 17 px 属真实结构还是原画误差 → UNKNOWN，未复制。
```

最后一行是关键：**单位报告也要带未解决项**，否则下游会默认全部已核对。
