# 工作流：从需求冻结到交付

这份流程来自实际交付过的 3D 打印浮雕项目（立绘 → 分层几何 → 体积并集 → STL → 切片建议）。核心不是「九步走完」，而是**每一步都有明确的准入条件、产物和证据**。

---

## 一、角色必须分离

同一个人不能既实现又验收。实际项目里一次性开四个角色：

| 角色 | 职责 | 明确禁止 |
|---|---|---|
| **builder**（建模者） | 写阶段脚本、建几何、出自检报告 | 不得编写自己的最终验收判据 |
| **verifier**（独立验证者） | 用**独立脚本**复测关键量（顶点级 / 射线级 / 行级） | 不得复用 builder 的自检脚本或中间量 |
| **reviewer**（审查者） | 对照原画与规格书逐项判 `PASS` / `FAIL` / `UNKNOWN` | 不得只读 builder 的结论就下判定 |
| **captain**（记录者 / 裁定者） | 维护台账、抽查、登记偏离；对争议项落裁定 | 被推翻时必须**如实登记**，不得掩饰 |

**为什么**：实现者与验收者共享同一个错误假设时，脚本会「验证」出错误结论。真实案例——某轮 builder 自报「IoU = 1.000000」，captain 用独立方法复测后该值不成立；另一轮 captain 自己的三处判断被 verifier 推翻，全部登记进台账。

**成本控制**：角色分离不等于全程四份工作。小项目可以只有 builder + 一个独立复测脚本（脚本**不读** builder 的中间产物，只读磁盘上的产物文件）。

---

## 二、项目文件机制

规则要落在文件里、由机制强制生效，而不是依赖参与者记忆。项目根目录固定放这几份：

```
<project>/
├── REQUIREMENTS.md      # 需求冻结：用户原话逐字 + REQ 编号 + 显式覆盖记录
├── DECISIONS.md         # 用户裁定：选项、含义、明确禁止项、已接受的风险
├── UNIT_CONVENTION.md   # 单位口径与 px↔mm 换算（唯一 source of truth）
├── OPEN_ITEMS.md        # 跨阶段待办台账：偏离、未建对象、争议项、UNKNOWN
├── review/
│   └── review_roundN.md # 每轮审查：判定、findings、下一轮目标
├── scripts/
│   ├── build_stageN_*.py    # 阶段构建（声明 STAGE_NAME）
│   └── check_stageN.py      # 该阶段的契约校验
├── builder/stageN_*.blend   # 阶段产物（默认不覆盖）
├── shots/                   # 证据图与 JSON 报告
└── DELIVERY.md              # 交付说明：清单 + 单位报告 + 未解决 UNKNOWN
```

四条硬规则：

1. **用户原话逐字保留**。`REQUIREMENTS.md` 开头是用户原话的逐字引用，后面才是你自己的 REQ 编号拆解。改写用户的话会让验收漂移。
2. **裁定不得静默推翻**。`DECISIONS.md` 里的每条裁定（含「已接受的风险」）与需求同级；下游要改，必须先报告「改什么 / 为什么 / 影响哪些下游」，等用户重新裁定。
3. **未知项留在台账上**。`OPEN_ITEMS.md` 与交付说明里的 `UNKNOWN` 清单只增不减，不得为了「分类完整」强行判定。
4. **偏离必须显式登记**。做了但和规格书不一致的地方，写清是哪一条、差多少、为什么；不登记 = 隐瞒。

模板见 `../templates/`。

## 三、九阶段建模流程

以「2D 原画 → 3D 打印浮雕」为例。每个阶段 = 一个构建脚本 + 一个校验脚本 + 一组证据图。

| 阶段 | 做什么 | 准入条件 | 产物 |
|---|---|---|---|
| 0 契约 | 单位口径、px↔mm 常数、坐标轴、往返预检 | — | `UNIT_CONVENTION.md` + 预检报告 |
| 1 块出 | 按语义分块，给每块一个深度层，只做**大形** | 契约预检通过 | `stage1_blockout.blend` + 正面对照图 |
| 2 体积 | 给平面块加**极浅圆弧**体积，不得改变正面轮廓 | 阶段 1 对照通过 | `stage2_volumes.blend` |
| 3 小部件 | 领子、徽章、腰带、扣具、武器等可辨识小件 | 阶段 2 深度预算够 | 同阶段 3 装配 |
| 4 结构线 | 只挑**真正代表结构**的线转几何（高度级差优先，不刻凸起边） | 上一步通过 | 结构线对象集 |
| 5 底座与装配 | 底座按实测尺寸、总高归一化到目标值 | 主体已定形 | `stage3_assembly.blend` |
| 6 对照 | 正面正交叠加 + 侧面厚度 + 22 项检查清单 | 阶段 5 完成 | 叠加图 / 差分图 / 判定表 |
| 7 水密合并 | 体素并集或布尔并集，清理碎屑与退化面 | 对照 `PASS` | 合并 `.blend` + 合并报告 |
| 8 导出与验收 | 导出 STL → **读回校验** → 掠射光 3/4 视角对照 | 合并报告通过 | `.stl` + 读回报告 + 交付说明 |

阶段 6 的对照是分水岭：在此之前都允许大改，在此之后只允许**最小修改**（见 `02` 的「最小修改原则」与「全量重建的条件」）。

## 四、每轮修改的循环（视觉校准模式）

```
改一项（只改一项）
  → 渲染截图（固定相机与光照，否则对比无意义）
  → 与原画对照（局部关系 + 整体观感，两路都要看）
  → 变好：保留并记录；变差：**回退**
  → 记录本轮范围与证据文件名
```

三条纪律：

- **一轮只改一项**。多项同改时，变差了你不知道是哪项造成的。
- **视觉上变差的尝试必须回退**，不因为「已经花了很多轮」而保留（真实案例：给部件加 Chaikin 圆角，部件变成圆滑卵石、结构全丢，已回退）。
- **轮次上限全项目唯一**。对照迭代最多 3 轮，写在同一个清单文件里，不另开计数器、不另开报告。到上限仍未达标的项，如实记为未达标并说明差距。

---

## 五、门（Gate）：什么时候可以放行

不要用「感觉差不多了」放行。可用的放行条件：

- 该阶段的**契约校验脚本全项通过**（例：某项目阶段校验 49/49、25/25），且校验脚本输出为 JSON 落盘；
- 关键量有**独立复测**（不由本阶段 builder 提供）；
- 该阶段声明的偏离与 `UNKNOWN` 已进台账；
- 若阶段产物会被下游覆盖，已按 `stage_guard.py` 的规则先备份旧产物。

不满足就停在原地修，不要带着未关闭的 `FAIL` 进入下一阶段——错误会沿链传播，事后返工成本远高于当轮修。

---

## 六、交付说明（DELIVERY.md）必含内容

1. **交付物清单**：路径、大小、`sha256`、是否覆盖旧文件；
2. **单位报告**：场景单位设置 + 导出单位 + 目标打印尺寸的换算链；
3. **拓扑闸门结果**：边界边、多面边、松散顶点、退化面的实测计数（水密性证据）；
4. **读回校验**：把导出文件重新导入，逐项比对（例：9/9 项）；
5. **合并后细节损失复查**：并集前后同一坐标的深度差、关键特征的定点探针；
6. **与原画的对照**：同口径的叠加/差分图，注明判定方法与不确定区间；
7. **切片与打印建议**：工艺、摆放方向、需要用户知情的取舍；
8. **未解决的 `UNKNOWN` 清单**：不得抹平；
9. **复现命令**：每一条可后台运行的命令原文。

第 8 条经常被省略，但它决定交付是「完成」还是「看起来完成」。
